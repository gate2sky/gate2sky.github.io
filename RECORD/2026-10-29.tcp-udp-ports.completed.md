# TCP and UDP ports per subdomain

Status: completed on branch `claude/charming-ramanujan-lzvg1g` (no PR yet).
The design below is what was built, with the differences listed here.

## What was built

- Config `tcp:` (`ports`, `max_ports` default 5, `listen_host`,
  `public_host` defaulting to the SSH host); migration 3, table `tcp_ports`
  (allow list space-separated, `preset`, `local_port`); lowest free port.
- `internal/ports`: TCP listeners and UDP sockets per forwarded port, allow
  lists per connection / per remote address, replace-on-reconnect, stats;
  closed with keys, owners, subdomains, ports and Disconnect (`manage`).
  UDP: a stream per remote address, 2 min idle, 512 at most, replies capped
  at 10× received + 64 KiB.
- `internal/udpframe`: `udp-forward@gate2sky` / `cancel-udp-forward@gate2sky`
  global requests and `udp@gate2sky` channels with length-prefixed
  datagrams.
- SSH: `-R <port>.<sub>:0:` (answers the public port), `-R <sub>:<public>:`
  and `-R <public>:`. **`-R <sub>:0:` stays HTTP** (no breaking change).
  Plain ssh on a UDP port is refused with a pointer to the client.
- Client: `internal/client` and `gate2sky tunnel SUBDOMAIN --server
  HOST:PORT [--http] [--tcp NAME=PORT] [--udp NAME=PORT] [-i] [--host-key]`
  (ssh-agent, ~/.ssh keys, known_hosts), reconnecting with backoff.
- `/tunnel.sh` served by the dashboard (`internal/web/templates/tunnel.sh`)
  with version, server and host key fingerprint; `--cache`,
  `GATE2SKY_DOWNLOAD_URL`, `GATE2SKY_VERSION`. Builds from source download
  the latest release.
- API `POST/PATCH/DELETE /api/subdomains/{name}/ports[/{id}]`; detail has
  `port_list`, `ports_command` (ssh), `tunnel_command` (curl | sh),
  `client_ip`; boot `tcp`.
- Windows: release builds `gate2sky-windows-{amd64,arm64}.zip` (in
  `SHA256SUMS`), `/tunnel.ps1` for PowerShell, agent over
  `\\.\pipe\openssh-ssh-agent`; the ports card switches between the
  Linux/macOS and Windows commands. The landing mentions ports.
- Dashboard: "Ports" card (`components/tcp-ports.html`) with TCP and UDP
  presets, add and edit dialogs; Admin column and range usage.
- Deploy/docs: Helm `tcp.*` (+ `tcp.udp`) and a `-tcp` LoadBalancer
  Service, compose, Dockerfile, example config, README.
- Tests: `TestTCPPorts`, `TestTCPPortsDisabled`,
  `TestClientForwardsHTTPTCPAndUDP`, `TestClientRefusedForwards`,
  `TestTunnelScript`, store/config/sshd/udpframe unit tests.

## Original design

Today `sshd.openTunnel` (`internal/sshd/conn.go`) only accepts remote port 0,
80 or 443 and answers anything else with "only HTTP tunnels are supported".
The README roadmap lists "TCP tunnels on dedicated ports".

## Agreed design

### Configuration

```yaml
tcp:
  ports: 30000-30099   # public port range; without it, no TCP/UDP ports
  max_ports: 5         # per subdomain
```

Docker publishes the range (`-p 30000-30099:30000-30099` and `/udp`); the Helm
chart gets a `LoadBalancer` Service for the range (Traefik would need an entry
point per port).

### Data

Table `tcp_ports`: subdomain, name (lowercase, unique per subdomain),
protocol (`tcp`/`udp`), public port (unique, allocated from the range and
stable), allow list (CIDRs; empty = anyone). Ports are created from the
dashboard only, never on connect, so the port is stable and access is set
before the service is reachable. The subdomain's SSH keys open all its ports.

### Dashboard: "TCP ports" card on the subdomain page

Between SSH keys and Delete subdomain. One row per port: name, address
`tcp://gate.example.com:30042` with copy, protocol, access ("Only these
addresses" with the current IP filled in by default, or "Anyone" with a
warning), online/idle status, edit, delete; a counter "2 of 5". Add form:
preset select, name, local port (only used to build the command), Add port.
Below, the ready-to-copy connect command for all the subdomain's ports.
Admin's Subdomains tab gets a TCP column and the range usage.

Presets (TCP unless noted; local port only feeds the shown command):

| Preset | Local port | Default access | Note |
|---|---|---|---|
| PostgreSQL | 5432 | IPs only | |
| MySQL / MariaDB | 3306 | IPs only | |
| Redis | 6379 | IPs only | warn: no auth by default |
| MongoDB | 27017 | IPs only | |
| SSH | 22 | anyone | |
| RDP | 3389 | IPs only | |
| VNC | 5900 | IPs only | warn: usually unencrypted |
| Minecraft (Java) | 25565 | anyone | |
| MQTT | 1883 | IPs only | 8883 with TLS |

| Valheim (UDP) | 2456 | anyone | needs `gate2sky tunnel` |
| WireGuard (UDP) | 51820 | anyone | needs `gate2sky tunnel` |
| Custom | — | IPs only | |

No port ranges for now: OpenSSH needs one `-R` per port anyway, and the usual
cases (passive FTP, RTP, multi-port games) fail for other reasons.

### Client: TCP with plain `ssh -R`

The forward request only carries the remote bind address and port (never the
local one), so the client names the port:

```bash
ssh -p 2222 -R db.myapp:0:localhost:5432 -R ssh.myapp:0:localhost:22 gate.example.com
ssh -p 2222 -R myapp:30042:localhost:5432 gate.example.com   # by public port
```

- `<name>.<subdomain>` as bind address with port 0, or the subdomain with its
  public port. With a single TCP port, `-R myapp:0:` would pick it; with
  several, refuse with
  "myapp has several TCP ports (db, ssh); choose one with -R <name>.myapp:0:localhost:<port>".
- Breaking change to settle: today `-R myapp:0:` opens an HTTP tunnel.
- Reply to port 0 with the public port (OpenSSH prints "Allocated port …").
- Console: `✔ tcp://gate.example.com:30042 (db) → localhost:5432` and the access.
- Server: on forward, listen on the public port; per accepted connection,
  check the allow list, open a `forwarded-tcpip` channel echoing the bind
  address/port, and copy both ways. Close the listener when the forward ends.
  HTTP and TCP forwards can share a connection.
- Hook into what closes tunnels today (`tunnel.Registry` users in
  `internal/manage`): key removed, user disabled/deleted, subdomain deleted,
  "Disconnect" in the dashboard.

### UDP: needs a gate2sky client

SSH only forwards TCP. Plan:

- Server listens on the UDP port and keeps a NAT-like table per remote
  (IP:port) with an idle timeout; each remote gets a custom channel
  (e.g. `udp@gate2sky`) to the client, carrying length-prefixed datagrams.
- Client: `gate2sky tunnel` subcommand of the same binary, authenticating with
  the usual SSH keys and agent (`-i` supported). One socket per remote towards
  `localhost:<port>`. It can also open HTTP and TCP forwards, so one command
  covers a whole subdomain:

  ```bash
  gate2sky tunnel myapp --http 3000 --tcp db=5432 --udp mc=19132
  ```

- `tunnel.sh` served by the server, run without installing:

  ```bash
  curl -fsSL https://gate.example.com/tunnel.sh | sh -s -- myapp --udp mc=19132
  ```

  It detects OS/arch, downloads the release matching the server's version
  (written into the script by the server), checks `SHA256SUMS`, runs it and
  deletes it on exit. **No cache by default** (temp dir from `mktemp -d`,
  removed with a trap); `--cache` keeps it in `~/.cache/gate2sky/<version>/`.
- Caveats to document: UDP over TCP suffers head-of-line blocking (fine for
  DNS, MQTT-SN, a quiet Bedrock server; jittery for fast games or VoIP); UDP
  sources can be spoofed, so allow lists protect less and replies must be
  rate- and size-limited against amplification; no Windows client yet
  (would need `tunnel.ps1` and Windows release binaries).
